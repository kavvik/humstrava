## OQ-001 — Локальное хранилище на ESP32

**Вопрос:** Что делать с тиками, если интернет недоступен?

**Варианты:**
- Кольцевой буфер в RAM (потеряется при перезагрузке, но быстро)
- Запись в flash/SPIFFS (не теряется, но flash имеет ограниченный ресурс записи)
- Карта microSD (если есть слот)
- Принять потерю данных при отсутствии сети (простейший MVP)

**Вопросы для решения:**
- Как долго хомяк может бежать без сети? (минуты / часы?)
- Сколько тиков влезет в RAM ESP32?
- Важна ли 100% полнота данных или "в основном всё" достаточно?

## OQ-017 — Таймзона для статистики

**Решено 2026-06-03.**

Backend timezone-agnostic: tick_ms хранится и возвращается всегда в UTC. Фронт конвертирует UTC → локальный timezone через `Intl.DateTimeFormat`. Границы "дня" для запросов вычисляет фронт → отправляет как UTC ms в параметрах `from`/`to`. Backend делает `WHERE tick_ms BETWEEN from AND to` без знания о таймзоне.

**Caveat (MVP → v2):** для MVP фронт использует браузерный timezone (работает пока хозяин дома). Если хозяин открывает дашборд из другой страны — браузерный timezone меняется, и статистика считается относительно чужого часового пояса. Правильное решение: хранить `device_timezone` (например, `Europe/Madrid`) в настройках устройства в БД. Фронт всегда использует timezone хомяка, а не свой текущий.

## OQ-018 — Граница сессии: 60 секунд

**Решено 2026-06-03.**

Не хардкодить — сделать настраиваемым параметром в UI. На графике показывать сырые паузы между тиками: пользователь сам видит "10 сек — просто осмотрелся" vs "5 мин — ушёл заниматься другим". Порог меняется ретроактивно (сессии не хранятся в БД, вычисляются из тиков). Дефолт: 3 минуты.

**Будущее:** проанализировать реальные данные из БД после нескольких недель работы — найти естественные кластеры пауз и определить порог эмпирически, а не с потолка.

## Решённые вопросы

- ✅ Диаметр колеса: 21 см
- ✅ Формат батча: абсолютные timestamp'ы в ms
- ✅ Сессии: вычисляются из сырых данных, не хранятся физически
- ✅ OQ-001 — Локальный буфер: RAM кольцевой буфер ~100 KB (~107 мин оффлайн). Теряем данные только при оффлайне > 107 мин или перезагрузке ESP32 во время оффлайна. Для хомяка достаточно.
- ✅ OQ-002 — Платформы: Railway Hobby $5/мес + Supabase free (PostgreSQL + Realtime) + Vercel free. Пауза Supabase не риск — хомяк бегает каждую ночь и держит базу активной. Итого ~$5/мес.
- ✅ OQ-003 — База "уснула": закрыт через OQ-001 + OQ-002. Хомяк держит базу активной. Если база всё же проснётся с задержкой 30 сек — RAM буфер ESP32 удержит тики.
- ✅ OQ-004 — Альтернативы хостингу: изучены. Выбран стек Railway + Supabase + Vercel ~$5/мес.
- ✅ OQ-005 — Идемпотентность: UNIQUE индекс по (device_id, tick_ms). Время на ESP32 через NTP при подключении к WiFi.
- ✅ OQ-006 — Безопасность: API key в заголовке X-API-Key. Ключ в ESP32 flash, проверка на бэкенде.
- ✅ OQ-007 — Дребезг геркона: программный дебаунс 100 мс на ESP32 в ISR. Тики ближе 100 мс игнорируются до попадания в буфер.
- ✅ OQ-008 — Скорость хомяка: worst case Роборовский 9.7 км/ч = 4.1 тик/сек. Дебаунс 100 мс безопасен (минимум 244 мс между тиками). Буфер = ~52 мин оффлайн (не 107 как считали). Хранилище = ~14 месяцев на free tier (не 2.5 года). Порода пользователя: Сирийский. Проект рассчитан на любую породу.
- ✅ OQ-009 — Диаметр колеса: 21 см подтверждён — измерен внутренний диаметр дорожки (поверхность бега). Окружность 65.97 см = 0.6597 м/тик. Все расчёты верны.
- ✅ OQ-010 — NTP fallback: сначала NTP (pool.ntp.org), если не ответил за 5 сек — GET /time у нашего бэкенда. Тики не отправляются пока нет времени. Flash хватает — удаление WebServer+ESPmDNS освобождает ~100–150 KB.
- ✅ OQ-011 — Railway sleep: режим сна опциональный, по умолчанию выключен. Просто не включать Serverless mode → FastAPI работает 24/7.
- ✅ OQ-012 — Стоимость Railway: 256 MB RAM 24/7 = ~$0.04/мес. Легко укладывается в $5 Hobby.
- ✅ OQ-013 — Supabase Realtime с прямыми вставками: работает. Realtime читает WAL (PostgreSQL Write-Ahead Log) — ловит любые INSERT независимо от клиента (psycopg2, asyncpg, SDK). Архитектура FastAPI → asyncpg → Supabase Realtime → фронт валидна.
- ✅ OQ-014 — Логика сессий и Telegram: in-memory кэш в FastAPI (dict {device_id: last_tick_ms}). Никаких лишних SELECT. При рестарте FastAPI — возможно одно лишнее Telegram уведомление (раз в несколько недель, приемлемо). В будущем для стартапа — Redis.
- ✅ OQ-015 — Telegram setup: только sendMessage, без polling/webhook. BOT_TOKEN + CHAT_ID в переменных окружения Railway. Сообщение: "🐹 Хомяк побежал! <ссылка на фронтенд>".
- ✅ OQ-016 — Индексы БД: отдельный индекс не нужен. UNIQUE constraint по (device_id, tick_ms) автоматически создаёт индекс в PostgreSQL — покрывает и дедупликацию и все аналитические запросы.
- ✅ OQ-017 — Таймзона: backend timezone-agnostic, всё в UTC. Фронт конвертирует через браузерный timezone (Intl.DateTimeFormat). Границы дня считает фронт, шлёт как UTC ms в from/to.
- ✅ OQ-018 — Граница сессии: настраиваемый параметр в UI, дефолт 3 мин. График показывает сырые паузы — пользователь видит сам. В будущем: эмпирически из реальных данных БД.
