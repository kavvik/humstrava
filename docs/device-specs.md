## Расчёт локального буфера тиков

Каждый тик = `int64` = **8 байт** (Unix timestamp в ms).

Бюджет на буфер — не более 50% свободной DRAM, чтобы оставить место для WiFi стека (~60 KB) и прочего:

```
Доступно:     272 KB
WiFi стек:    ~60 KB
Другое:       ~20 KB
Под буфер:    ~100 KB → 12 800 тиков
```

**Максимальная скорость хомяка:**
- Хомяк бегает ~2–3 км/ч
- Длина окружности колеса: 65.97 см
- Тиков в секунду при 3 км/ч: `(3000 м / 3600 с) / 0.66 м ≈ 1.26 тик/сек`
- Пиковый реалистичный максимум: ~2 тик/сек

**Ёмкость буфера при 2 тик/сек:**
```
12 800 тиков / 2 тик/сек = 6 400 сек ≈ 107 минут оффлайн
```

При 50 KB буфере (консервативно):
```
6 400 тиков / 2 тик/сек ≈ 53 минуты оффлайн
```

## Файловая система (SPIFFS / LittleFS)

Flash 4 MB минус раздел скетча (1.25 MB) = ~2.75 MB под файловую систему.
Стандартная partition table ESP32 оставляет **1.5 MB под SPIFFS**.

При записи тиков в SPIFFS:
```
1 500 000 байт / 8 байт = 187 500 тиков
187 500 / 2 тик/сек = 93 750 сек ≈ 26 часов оффлайн
```

⚠️ Flash имеет ресурс ~100 000 циклов записи. При постоянной записи это не проблема,
но нужно писать блоками, а не по одному байту.

## Ограничения для разработки

| Ограничение | Значение |
|---|---|
| Не занимать под буфер > 100 KB DRAM | иначе WiFi нестабилен |
| SPIFFS писать блоками, не тик-за-тиком | продлевает ресурс flash |
| Heap fragmentation | при частых malloc/free — использовать статичный массив |
| Watchdog timer | долгие операции в loop() вызывают сброс — ISR для геркона обязателен |

## Рекомендуемый подход к буферу

```
Уровень 1 (RAM): кольцевой буфер на 500–1000 тиков (4–8 KB)
  → отправляется каждую секунду по WiFi

Уровень 2 (SPIFFS): сброс при потере WiFi
  → восстанавливается и досылается при восстановлении соединения
```
