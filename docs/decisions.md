## ESP32

**Время:** NTP (pool.ntp.org) при подключении к WiFi. Если NTP не ответил за 5 сек — fallback: GET /time у бэкенда. Не отправлять тики пока время не получено ни одним из способов.

**Буфер:** RAM кольцевой буфер на ~100 KB (~12 800 тиков). Оффлайн ёмкость: ~52 мин при максимуме (Роборовский 9.7 км/ч), ~71 мин для Сирийского.

**Дебаунс:** программный, 100 мс, в ISR на ESP32. Тики ближе 100 мс к предыдущему игнорируются до попадания в буфер.

**Отправка:** батч раз в 1 секунду, только если есть тики. При ошибке — не очищать буфер, повторить в следующую секунду.

**Аутентификация:** заголовок `X-API-Key: <key>`. Ключ хранить в ESP32 flash.

---

## Формат батча (ESP32 → Backend)

```json
{
  "d": "hamster-wheel",
  "ticks": [1748945201123, 1748945201456, 1748945201789]
}
```

- `d` — device_id
- `ticks` — массив Unix timestamp в миллисекундах, по одному на каждый оборот колеса

**Endpoint:** `POST /ticks`
**Header:** `X-API-Key: <key>`

---

## База данных

**Основная таблица:**
```sql
CREATE TABLE ticks (
  id          BIGSERIAL PRIMARY KEY,
  device_id   TEXT NOT NULL,
  tick_ms     BIGINT NOT NULL,
  created_at  TIMESTAMPTZ DEFAULT NOW(),
  CONSTRAINT unique_tick UNIQUE (device_id, tick_ms)
);
```

**Вставка (идемпотентная):**
```sql
INSERT INTO ticks (device_id, tick_ms)
VALUES (...)
ON CONFLICT (device_id, tick_ms) DO NOTHING;
```

**Индексы:** отдельные индексы не нужны. UNIQUE constraint по (device_id, tick_ms) автоматически создаёт B-tree индекс в PostgreSQL — покрывает дедупликацию и все аналитические запросы (фильтр по устройству + диапазон времени).

## Параметры колеса

- Диаметр: 21 см
- Длина окружности: π × 21 = **65.97 см**
- 1 тик = 1 оборот = **0.6597 м**
- Скорость (км/ч) = `(тиков_в_секунду × 0.6597 × 3.6)`

---

## Сессии

Не хранятся в БД. Вычисляются из тиков по правилу:
> gap между соседними тиками > N секунд = граница сессии

N — настраиваемый параметр, по умолчанию **60 секунд**.

---

## Real-time

Supabase Realtime: фронтенд подписывается на INSERT в таблицу `ticks`.
Новый тик → фронт получает событие → обновляет скорость и график без polling.

---

## Telegram

- Уведомление при старте сессии (первый тик после gap > N секунд)
- Текст: "🐹 Хомяк побежал! [ссылка на фронтенд]"
- Логика: in-memory кэш `{device_id: last_tick_ms}` в FastAPI. Сравниваем первый тик батча с кэшем. Если gap > N сек → новая сессия → Telegram. Нет лишних SELECT к БД.
- При рестарте FastAPI кэш сбрасывается → возможно одно лишнее уведомление (приемлемо)
